## 1. 품질·완료 선언에 대한 핑계

| 핑계 | 현실 |
|---|---|
| "돌아가니까 됐다" | 돌아가도 읽기 어렵거나 ADR 위반이거나 보안 구멍이면 빚이 복리로 쌓인다. "동작"은 5축(정확성·가독성·구조·보안·테스트) 중 하나일 뿐. |
| "내가 짰으니 맞는 걸 안다" | 작성자는 자기 가정에 눈먼다. 변경마다 **fresh-context 한 번**(`/code-review` 또는 새 검토)이 사각을 잡는다. |
| "나중에 정리하자" | 나중은 안 온다. 리뷰가 품질 게이트다 — 머지 **전에** 고친다. CLAUDE.md §3 `# TODO: 나중에` placeholder 금지와 동일. |
| "테스트 통과하니 좋다" | 테스트는 필요조건이지 충분조건이 아니다. 구조·보안·실행 이음새(GPU로드·프로세스spawn·실DB enum)는 단위테스트가 못 잡는다 — 회고 §4-3, 실세션 하니스 정신. |
| "단위테스트 통과 = 실행도 됨" | mock 단위는 실 GPU·stdio·실DB 경로를 안 건드린다. 실행 이음새 의심되면 `scripts/verify_session.py`/`verify_scenarios.py` 로 **실세션 게이트**를 돌린다. |

## 2. 의심·검토를 건너뛰는 핑계

| 핑계 | 현실 |
|---|---|
| "확신하니 검토 생략" | 확신은 정확성과 약하게만 상관한다. 확신의 순간이 사각이 숨는 자리. novel 한 결정일수록 의심. |
| "리뷰는 트집만 잡을 것" | 스코프를 안 줬을 때만. "계약(ADR·DoD)을 깨뜨릴 이슈만" 으로 제한하면 신호만 남는다. |
| "끝나고 `/review` 로 한 번에" | 잘못된 방향은 일찍 잡아야 교정이 싸다. 회고 §4-1 "표면 vs 근본 5분 멈춤" — PR 시점엔 이미 늦다. |
| "모든 단계를 의심하면 못 끝낸다" | 의심은 **non-trivial 결정**에만. 한 줄 rename·포매팅엔 fresh-context 리뷰 낭비(레드플래그). |
| "리뷰어가 반대했으니 내가 틀림" | 반대는 정보지 판결이 아니다. 산출물(코드·ADR)을 다시 읽고 분류한 뒤 **내가** 결정. |
| "3번째 고쳐도 안 되네, 또 시도" | 같은 자리 3사이클 넘기면 멈추고 사용자에게 에스컬레이트 — 회고 §4-4 "그만하기 결정 의식". |

## 3. 이 프로젝트 특화 핑계

| 핑계 | 현실 |
|---|---|
| "ADR 살짝 어긋나도 괜찮겠지" | ADR/PRD 충돌은 **임의 변경 금지, 멈추고 보고**(CLAUDE.md §3·§10). v3 ADR과 충돌 시 v4 우선(ADR-021). |
| "프롬프트만 조금 바꿨으니 ollama 테스트 생략" | 프롬프트/coach_response/ollama_service/config.llm 변경은 `pytest -m ollama` **필수 게이트**(메모리 feedback-llm-ollama-test-gate). 9b 의 JSON/ConfirmRule 회귀는 단위가 못 본다. |
| "혹시 모르니 추상화 레이어 하나" | YAGNI. 1인·단일사용자 프로젝트(ADR-002)에 미래 대비 추상화·`user_id`·인증은 금지(CLAUDE.md §3). |
| "사람 검증 남았지만 막아서 멈춤" | 사람 E2E 는 phase 진행을 **안 막는다**(메모리 feedback-manual-qa-nonblocking). 자동으로 최대한 대체하고 순수 수동만 백로그에 누적 후 마일스톤 일괄. |
| "버그 하나 잡고 바로 커밋" | 3~4개 모아 패턴을 본다(회고 §4-2). 단, diff 는 작게 + 변경마다 즉시 검증(회고 §4-5). |

## 4. 레드 플래그 (보이면 멈춤)

- 테스트 통과만 확인하고 다른 축(구조·보안·가독성·ADR)은 안 본 "리뷰"
- 증거 없는 "다 됐어요" / "LGTM" — 무엇을 어떻게 검증했는지 문장으로 없음
- 한 줄 rename·포매팅에 fresh-context 리뷰 (과잉)
- 같은 산출물을 안 바꾸고 다시 리뷰 돌리기 / 같은 버그 3사이클 초과
- 리뷰어에게 "이거 좋아?"(동의 유도) 대신 "이슈 찾아"(적대적)로 안 물음
- 버그 수정 PR 인데 회귀 테스트 없음
- 시간 압박을 이유로 high-stakes 결정의 의심을 생략
- 실행 이음새(GPU·spawn·stdio·실DB) 의심되는데 mock 단위만 돌리고 실세션 하니스 생략

## 5. 완료 선언 전 검증 체크 (증거 우선)

작업을 "완료"라 부르기 전:

- [ ] 변경이 닿는 **모든 5축** 점검(A~H 체크리스트로 cross-check)
- [ ] Critical/Important 이슈 = 해결, 또는 근거와 함께 명시적 보류
- [ ] 관련 테스트 통과 (비-GPU pytest / `-m ollama`(해당 시) / UI vitest)
- [ ] 빌드 성공 (`tsc` + `vite build`, 백엔드 `ruff`)
- [ ] 실행 이음새 의심 시 실세션 하니스 PASS
- [ ] **검증 스토리 문서화** — 무엇을 바꿨고 어떻게 확인했는지 완료 보고에 명시(CLAUDE.md §9 형식)
